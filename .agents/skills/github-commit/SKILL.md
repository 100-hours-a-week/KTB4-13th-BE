# Git Commit

## 변경 확인

저장소 루트의 [Git 규칙](../../../.docs/.conventions/GIT_CONVETIONS.md)을 읽는다.
`git status --short`, 현재 브랜치, `git diff`, `git diff --cached`와 관련 미추적 파일을 확인한다.
기존에 스테이징된 변경과 이번 요청 범위를 구분한다.

관련 Issue 번호는 사용자 입력 또는 `<type>/<issue-number>-<summary>` 브랜치에서 확인한다.
번호가 없거나 서로 다르면 한 번 질문한다. 번호를 추측하거나 PR 번호로 대체하지 않는다.
현재 브랜치가 `main`이면 직접 커밋하지 않고 Issue에 연결할 작업 브랜치를 먼저 정한다.

## 메시지와 실행

1. 하나의 논리적 변경을 한 커밋으로 묶는다. 분리 가능한 변경은 파일 또는 hunk 단위로 구분한다.
2. 제목은 `<type>: <한국어 요약>(#<issue-number>)`로 작성한다. 허용 유형은 `feat`, `fix`, `refactor`, `test`, `docs`, `chore`다. 요약 끝에 마침표를 붙이지 않고, `WIP`나 단독 `update`·`change`를 사용하지 않는다. 필요하면 빈 줄 다음에 변경 이유를 본문으로 작성한다.
3. 변경에 맞는 검증을 실행하고 결과를 확인한다. 규칙 검사는 `.github/workflows/git-conventions.yml`을 참고한다. 명령형 표현과 변경의 논리적 단위는 사람이 판단해야 한다.
4. 실제 커밋이 명시적으로 요청되었을 때만 실행한다. 메시지 추천 요청이면 초안을 반환한다. 이미 승인한 범위는 다시 묻지 않는다.
5. 승인된 경로만 명시적으로 스테이징하고 최종 staged diff를 확인한다. `git add .`로 무관한 변경을 포함하거나 기존 스테이징을 임의로 해제하지 않는다. 기존 staged 변경이 범위 밖이면 이를 보존할 방법을 정한 뒤 진행한다.
6. `.env` 등 비밀값, 빌드 산출물, 개인 설정을 제외한다. `.docs/`는 명시적인 게시 요청이 있을 때만 포함한다. 요청하지 않은 AI 기여 표기를 추가하지 않는다.
7. 메시지는 임시 UTF-8 파일에 저장해 `git commit -F`로 전달한다. 훅을 우회하거나 기존 커밋을 자동으로 amend·rebase하지 않는다. Push는 별도 요청 범위에서만 수행한다.

## 완료

커밋 SHA, 제목, 포함한 파일 범위와 검증 결과를 보고하고 `git status --short`로 남은 변경을 확인한다.
실패하면 원인을 보고하고 같은 작업을 무조건 재시도하지 않는다.
