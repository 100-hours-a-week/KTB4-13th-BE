# GitHub Issue

## 기준과 입력

저장소 루트의 [Git 규칙](../../../.docs/.convetions/GIT_CONVETIONS.md)을 먼저 읽는다.
`git remote -v`와 `gh repo view`로 대상 저장소를 확인한다. 다른 프로젝트의 저장소명이나 라벨을 가져오지 않는다.

유형에 맞는 `.github/ISSUE_TEMPLATE/` 파일을 읽는다.
`feat`는 `feature.yml`, `fix`는 `bug.yml`, `docs`는 `docs.yml`,
`refactor`·`test`·`chore`는 `chore.yml`을 사용하되 제목의 유형은 유지한다.

## 작성과 생성

1. 사용자 요청과 관련 코드에서 배경, 목표, 범위, 완료 조건을 확인하고 기존 이슈와 중복되는지 검색한다.
2. 제목은 `<type>: <요약>`으로 작성한다. 템플릿의 각 입력 항목을 `### {label}` 섹션으로 바꾸고 필수 항목을 채운다. 설명과 Agent prompt에 관련 경로·제약·검증 방법을 담고, 완료 조건은 관찰 가능한 결과로 작성한다.
3. 본문은 한국어로 작성한다. 불확실한 요구사항은 사실처럼 채우지 않고 꼭 필요한 정보만 질문한다. 로컬 `.docs/` 원문이나 비밀값을 외부 본문에 복사하지 않는다.
4. `gh label list`로 실제 라벨을 확인한다. 템플릿에 지정된 라벨이 없으면 그 사실을 알리고 해당 라벨을 생략한다. 라벨 생성이나 triage 상태 변경은 요청 범위에 있을 때 수행한다.
5. 생성·수정이 명시적으로 요청되었으면 정리한 내용으로 실행한다. 초안 요청이나 스킬 자동 선택 자체는 게시 승인이 아니다. 게시 요청이 없다면 제목·본문·라벨을 완성해 보여준 뒤 생성 의사를 확인한다. 이미 승인된 작업은 다시 확인받지 않는다.
6. CLI를 사용할 때 본문은 임시 UTF-8 파일에 저장해 `gh issue create --body-file` 또는 `gh issue edit --body-file`로 전달한다. 결과가 불확실하면 목록을 재조회해 중복 생성 여부를 확인한다.

Issue 생성과 Branch 생성은 별도 작업이다. Branch까지 요청받았다면 관련 Issue 번호와 최신 `main`을 확인하고 `<type>/<issue-number>-<kebab-case-summary>`로 만든다. 기존 변경을 덮거나 자동으로 커밋하지 않는다.

## 완료

생성·수정한 Issue의 번호와 URL, 적용한 라벨을 보고한다. 초안만 작성했으면 아직 게시하지 않았음을 명시한다.
