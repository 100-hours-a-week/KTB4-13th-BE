# 주문 도메인 규칙

이 문서는 주문 생성·취소의 업무 정책과 미확정 문서 불일치를 기록합니다. API 경로·HTTP 입력은 코드의 `api/spec`, 테이블 정의는 ERD와 Flyway를 함께 확인합니다.

## 1. 주문 경로와 배송지

- 구매는 활성 장바구니 → 주문 생성 → 결제의 경로만 허용합니다. 상품 상세에서 바로 주문하지 않습니다.
- 주문 요청의 `items[].itemId`는 상품 ID입니다. 각 상품은 요청 회원의 활성 장바구니에 담겨 있어야 합니다.
- 전체 장바구니가 아니라 장바구니에서 선택한 상품만 주문할 수 있습니다.
- 주문 요청에는 배송지 ID가 필수입니다. 회원이 소유한 활성 배송지만 사용할 수 있고 기본 배송지로 대체하지 않습니다.
- 주문을 생성할 때 `order_addresses`에 배송지 스냅샷을 저장합니다. 우편번호는 ERD의 `VARCHAR(5)`를 따릅니다. 기존 주소 우편번호가 5자를 초과하면 주문을 거부하고, 숫자 형식은 추가로 검증하지 않습니다.

## 2. 금액·재고·상태

- 주문상품 단가는 주문 생성 시 서버가 확인한 상품의 현재 `discounted_price`입니다.
- 주문상품 금액은 단가 × 요청 수량이고, 주문 금액은 주문상품 금액의 합입니다. 배송비·쿠폰·포인트는 이 주문 생성 범위에 포함하지 않습니다.
- 요청 상품은 활성 상품·도서여야 하며, 요청 수량이 현재 재고를 넘으면 `E8001 INSUFFICIENT_PRODUCT_STOCK`로 주문을 거부합니다.
- 주문 생성 중에는 재고를 차감하거나 예약하지 않습니다.
- 결제 확정 시점에 상품별 재고를 원자적으로 다시 검증·차감합니다. 재고가 부족하면 결제를 확정하지 않으며, 부분 주문이나 백오더를 허용하지 않습니다. 이 흐름은 결제 기능 구현 범위입니다.
- 결제 실패·취소·환불 후 재고 복구 기준과 처리 시점은 결제 기능을 구체화할 때 결정합니다.
- 새 주문과 주문상품의 초기 상태는 `CREATED`입니다. 결제 승인·취소 상태 전이는 이 API에서 수행하지 않습니다.
- 주문 생성은 배송지 스냅샷, 주문, 주문상품을 한 쓰기 트랜잭션으로 저장합니다. 장바구니 항목을 삭제하거나 수량을 변경하지 않습니다.

## 3. API·인증 계약

- 주문 생성 경로는 최신 확정 계약인 `POST /api/v1/orders`입니다.
- Notion의 응답 예시는 `result/data/error` 외피지만, 구현 응답은 프로젝트의 `ApiResponse` 계약을 따릅니다.
- 회원 식별은 Bearer Access Token의 JWT Principal에서 가져오며 client가 `userId`를 전달하지 않습니다.
- 장바구니에 없는 상품은 API 명세의 `E3000 PRODUCT_MISMATCH_IN_ORDER`로 거부합니다. 주소 소유권 위반은 프로젝트의 `E403 FORBIDDEN`을 따릅니다.

## 4. 확인 필요

- API 요청 수량이 장바구니에 저장된 수량을 초과할 수 있는지는 명세에 없습니다. 현재 구현은 활성 장바구니에 상품이 있는지 확인하고, 요청 수량은 서버 재고와 비교합니다.
- 같은 상품 ID가 `items`에 여러 번 포함될 때의 병합·거부 정책은 명세에 없습니다. 현재 구현은 입력 행을 각각 주문상품으로 저장하고 재고 확인 시 수량을 합산합니다.
- ERD는 `orders.user_id`를 회원 테이블 FK로 표시하지만 최신 Flyway에는 회원 테이블이 없습니다. 이번 마이그레이션에서는 존재하지 않는 테이블을 참조하는 FK를 만들지 않습니다. 회원 스키마가 추가될 때 연결을 확인해야 합니다.
- ERD에서 `orders.key`는 UNIQUE이면서 NULL 허용입니다. 이번 API는 주문키를 생성해 응답하지만, 마이그레이션은 ERD의 nullable 제약을 유지합니다.
- 상품·도서의 활성 여부는 `deleted_at IS NULL`로 확인하고, 주문 가능 수량은 `stock_quantity`로 검증합니다. `orders.status`와 `order_item.status`는 `CREATED` 등 업무 진행 상태이므로 삭제 시각과 별도로 유지합니다.
- ERD는 주문 금액 설명에 배송비·포인트를 언급하지만 이번 주문 생성 금액 정책에서는 제외하기로 했습니다. 결제 금액 정책은 결제 기능 정의 시 다시 확인해야 합니다.
- Notion API 오류 목록에는 기존 상품 조회의 `E404 PRODUCT_NOT_FOUND`가 없습니다. 활성 상품·도서 조회 실패는 기존 상품 UseCase 오류를 따르며 API 명세와의 오류 계약은 확인이 필요합니다.
- 제공된 세 번째 도메인 초안은 주문이 아닌 상품 도메인 문서입니다. 별도 주문 도메인 문서도 미완성 템플릿이므로, 결제 실패 재시도·멱등성은 결제 기능을 정의할 때 결정합니다. 재고 차감 시점은 [ADR-0002](../../docs/adr/0002-cart-inventory-non-reservation.md)를 따릅니다.

## 5. 주문 전체 취소

- 주문 소유자는 `DELETE /api/v1/orders/{orderKey}/cancel`로 결제 전 주문 전체를 취소합니다. 요청 본문과 취소 사유는 없습니다.
- 취소 대상은 요청 회원 소유의 활성 주문이며, 주문과 모든 주문상품의 업무 상태가 `CREATED`일 때만 허용합니다. 주문·주문상품을 `CANCELED`로 전이하고 `orders.canceled_at`을 기록합니다.
- 주문 및 주문상품 변경은 하나의 쓰기 트랜잭션에서 처리합니다. 주문 행 잠금으로 같은 주문의 동시 취소를 직렬화하고, 첫 취소 후 도착한 요청은 상태 충돌로 거부합니다. 중복 요청도 성공으로 처리하지 않습니다.
- 주문 없음은 404 `ORDER_NOT_FOUND`, 소유자 불일치는 403 `E403`, 취소할 수 없는 상태와 중복 취소는 409 `ORDER_CANNOT_BE_CANCELED`로 응답합니다. 성공 응답은 기존 `ApiResponse<Void>` 계약을 사용합니다.
- 결제·환불, 재고 복구, 쿠폰·포인트 정산, 장바구니 복원은 이 기능에서 수행하지 않습니다. 주문 금액과 상품 스냅샷은 변경하지 않습니다.
- 취소 요청도 Bearer Access Token의 JWT Principal로 주문 소유자를 식별합니다.

### 취소 문서 확인 필요

- 전달된 Notion API 명세 링크는 취소 API 계약을 확인할 수 없었습니다. 검색 가능한 다른 주문 문서에는 주문 전체·부분 취소 경로가 다르게 적혀 있고, 결제 API 문서에는 결제 취소 API가 별도로 있습니다. 이번 구현은 승인된 주문 전체·결제 전 취소 계약을 따르며, API 경로와 공개 오류 코드의 Notion 명세 대조는 확인이 필요합니다.
- 검색 가능한 Notion ERD에는 `cancel` 및 `cancel_balance` 구조가 있고 `payment_id`와 금액 컬럼이 필수로 표시되어 있습니다. 현재 Flyway에는 결제 테이블이 없고 이번 기능은 결제 전 취소이므로 이를 추가하지 않습니다. ERD의 결제 취소 원장 구조와 실제 스키마의 차이는 확인이 필요합니다.
