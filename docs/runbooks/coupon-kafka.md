# Kafka 쿠폰 발급 운영

발급 API는 Redis Lua로 재고를 차감하고 사용자를 예약한 뒤 Kafka에 직접 발행합니다. Kafka 전송 성공을 확인하면 `202`를 반환합니다. 쿠폰함은 소비자가 MySQL 발급 저장을 커밋한 뒤 갱신됩니다.

## 기존 테스트 요청 확인과 전환

1. 대상 환경에서 기존 Stream 경로로 접수한 테스트 요청이 있었는지 확인합니다. 사용 이력이 없다면 새 버전으로 전환합니다.
2. 사용 이력이 있다면 추가 테스트 요청을 넣지 않고, 이미 처리 중인 발급 API 요청이 끝났는지 확인합니다. 인계가 끝날 때까지 기존 버전의 릴레이를 계속 실행합니다. 기본 Stream 키는 `coupon:issuance:kafka-outbox`입니다. 환경에서 키를 변경했다면 해당 키로 조회합니다.

   ```text
   XINFO GROUPS coupon:issuance:kafka-outbox
   XPENDING coupon:issuance:kafka-outbox coupon-kafka-relay
   ```

3. `coupon-kafka-relay` 그룹의 `lag`(미전달)와 `pending`(미확인)이 모두 0이면 Kafka 인계가 끝났으므로 새 버전으로 전환합니다. 그룹이 없거나 `lag`가 확인되지 않으면 완료로 판단하지 않습니다. Stream 항목은 ACK 뒤에도 남으므로 Stream 길이는 완료 기준으로 사용하지 않습니다.

## 처리 지연과 장애

- Redis 예약 뒤 Kafka 전송 결과를 확인할 수 없으면 발급 API는 `COUPON_ISSUE_FAILED`를 반환하고 예약을 유지합니다. 타임아웃 뒤에도 늦게 전송될 수 있고, 예약 직후 앱이 종료되면 Kafka에 도착하지 않은 예약이 남을 수 있습니다. 대사의 `pendingReservations`와 Kafka 소비 지연, DLT 기록을 함께 확인합니다.
- 브로커는 `KAFKA_BOOTSTRAP_SERVERS`로 지정합니다. 토픽 생성 전 `coupon.kafka.replicas`와 `coupon.kafka.min-in-sync-replicas`를 환경에 맞춥니다. 로컬 기본값은 각각 1입니다.
- Stream에서 Kafka로 넘긴 테스트 요청의 최종 발급은 MySQL에서 확인합니다. Kafka 소비자 그룹은 `book-coupon-issuance-redis`입니다. 소비 재시도를 소진한 요청은 `book.coupon-issuance.redis.v1.DLT`에 남습니다.

## 행사 마감 직전 접수

- `202`는 발급 요청이 접수됐다는 뜻입니다. 안내 문구 예시는 “쿠폰 발급 요청을 접수했습니다. 발급이 완료되면 쿠폰함에서 확인할 수 있으며, 사용 기한은 행사 종료 시각까지입니다.”입니다.
- 접수 후 소비가 늦어지면 행사 종료 뒤에도 MySQL에 발급이 반영됩니다. 쿠폰함에는 `ISSUED` 상태와 이미 지난 `expiredAt`이 함께 표시됩니다. 화면에서 사용 가능 여부를 안내할 때는 만료 시각도 확인합니다. 예를 들어 “쿠폰은 발급됐지만 행사 종료로 사용할 수 없습니다.”라고 표시할 수 있습니다.
- 결제 후보는 현재 시각이 `expiredAt`보다 앞선 쿠폰만 포함합니다. 만료된 보유 쿠폰 ID를 결제 생성에 보내면 `400/E5000`(사용할 수 없는 쿠폰입니다)이 반환됩니다.
- 발급일 기준 유효기간이 필요한 유형을 도입할 때 접수 시 확정한 만료 시각을 메시지와 보유 쿠폰에 저장할지 검토합니다.

## 실패 건 선별 재발행

실패 토픽의 메시지 원문과 예외 유형은 `issuance_dlt_log`에 저장됩니다. DB 기록에 실패하면 소비자는 같은 메시지를 다시 읽습니다. 예외 원문과 스택은 실패 토픽에 싣지 않습니다.

권한 있는 운영자는 원인을 해결하고 미발급 상태를 확인한 뒤 필요한 ID만 선택합니다.

```sql
SELECT id, error_type, received_at, replayed_at
FROM issuance_dlt_log
WHERE replayed_at IS NULL
ORDER BY received_at DESC
LIMIT 100;

```

모든 운영 인스턴스에서 `coupon.admin.user-ids`에 재발행 권한을 가진 JWT 사용자 ID를 설정합니다. 원인을 해결한 후 `POST /admin-api/v1/coupons/issuance-dlt/replay`에 `{"ids":[123]}`을 보냅니다. 한 번에 최대 100건을 선택할 수 있습니다.

재발행 작업은 기존 메시지 키와 원문을 사용하고, Kafka 확인 후 `replayed_at`을 기록합니다. 이 시각은 재발행 완료를 뜻하므로 최종 발급은 DB에서 확인합니다. 재발행 결과가 불확실하면 같은 메시지가 다시 전달될 수 있으며, 소비자는 기존 발급을 확인해 중복 반영을 막습니다. 다시 실패한 건은 새 실패 기록으로 남고 운영자가 선택할 때까지 대기합니다.

## 쿠폰 재고 대사

대사할 쿠폰 ID를 `COUPON_RECONCILE_COUPON_IDS=123,456`으로 지정하면 해당 인스턴스에서만 정기 대사를 실행합니다. 기본 간격은 60초이며 `coupon.reconcile.delay-ms`로 조정합니다. 같은 쿠폰을 여러 인스턴스에서 중복 조회하지 않도록 대상은 운영 담당 인스턴스에만 지정합니다.

Redis 예약 사용자 중 MySQL 보유 쿠폰 행에 없는 사용자를 미반영 예약으로 집계합니다. 삭제 처리된 보유 쿠폰도 이미 발급된 이력에 포함합니다. `전체 수량 - DB 발급 수량 - 미반영 예약 - Redis 잔량`이 0인지 확인하고, DB 발급 수량과 보유 쿠폰 행 수도 따로 대조합니다.

| 결과 | 의미 |
| --- | --- |
| `MATCHED` | DB 발급과 Redis 잔량이 일치하고 미반영 예약이 없습니다. |
| `PENDING` | 수량 차이가 Redis의 미반영 예약으로 설명됩니다. 실패 토픽에 남은 건도 포함될 수 있으므로 큐와 실패 기록을 확인합니다. |
| `DRIFT` | 미반영 예약을 제외해도 수량 차이가 남거나, DB 발급 수량·보유 행 또는 매진 신호에 불일치가 있습니다. |
| `REDIS_STOCK_MISSING` | Redis 잔량 키가 없습니다. 재고 0장으로 처리하지 않습니다. |
| `SNAPSHOT_CHANGED` | DB 조회 전후 Redis 스냅샷이 달라 수량 차이 판정을 보류했습니다. |

수량과 발급 건수가 일치하고 미반영 예약이 없으면 Redis 발급자 누락과 매진 신호만 보정합니다. Redis 상태가 보정 직전에 바뀌면 다음 대사로 미룹니다. 실제 수량 차이는 운영자가 확인하며 대사가 수량을 바꾸지 않습니다. 지정한 쿠폰의 예약 사용자와 DB 발급 이력을 읽으므로 필요한 쿠폰에 한해 사용합니다. 두 저장소에서 함께 사라진 접수까지 확인할 수는 없습니다.
